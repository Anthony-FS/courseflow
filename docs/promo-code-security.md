# วิธีนำระบบความปลอดภัยของ Promo Code ขึ้นใช้งาน

การเปลี่ยนแปลงนี้ครอบคลุมการตรวจสอบ promo code และการสร้าง/แก้ไข promo ของ admin
ไม่ได้เปลี่ยนสิทธิ์การลงทะเบียนเรียน เจ้าของรายการชำระเงิน เนื้อหาคอร์ส หรือโปรไฟล์
ส่วน API สร้างรายการชำระเงินปรับเฉพาะการตอบสถานะ `429` และ `Retry-After`
เมื่อการตรวจ promo เกินโควตา

## ขั้นตอนนำไปใช้บน Supabase

1. เข้าสู่โปรเจค Supabase ที่เว็บเชื่อมอยู่ ด้วยบัญชีเจ้าของฐานข้อมูล
   เปิด **SQL Editor** แล้วคัดลอกเนื้อหาจากไฟล์
   `docs/sql/025_promo_code_security.sql` ไปวางและกด **Run**
   ต้องรันไฟล์ปรับโครงสร้างฐานข้อมูลก่อนหน้าจนถึงหมายเลข 024 มาแล้ว
   ไฟล์นี้ทำงานเป็น transaction คือสำเร็จพร้อมกันทั้งชุด หรือย้อนคืนเมื่อเกิดข้อผิดพลาด
   และสามารถรันซ้ำได้
2. นำโค้ดเว็บเวอร์ชันที่แก้ promo ขึ้นใช้งานในช่วงเดียวกัน
   โค้ดเว็บเก่าที่อ่าน promo โดยตรงด้วยสิทธิ์นักเรียนจะใช้วิธีเดิมไม่ได้หลังรัน SQL
   ส่วนโค้ดเว็บใหม่จะตอบ `503` เมื่อมีการตรวจหรือบันทึก promo หากยังไม่ได้รัน SQL
   ระบบจะไม่ย้อนกลับไปใช้วิธีอ่านข้อมูลเดิมที่มีช่องโหว่
3. ลองใช้งานด้วยบัญชีนักเรียน ตรวจว่ากด **Apply** ได้ตามปกติ
   เมื่อครบ 10 ครั้งแล้ว ครั้งที่ 11 ต้องถูกจำกัด และต้องลองใหม่ได้เมื่อพ้นช่วง 60 วินาที
   ทั้งโค้ดที่ใช้ได้และโค้ดที่ใช้ไม่ได้จะถูกนับรวมกัน
   การจ่ายเงินโดยใช้ promo ใช้โควตาเดียวกัน ส่วนการจ่ายเงินโดยไม่ใช้ promo จะไม่หักโควตานี้
4. ตรวจว่าคนที่ยังไม่ล็อกอินและบัญชีนักเรียนไม่สามารถอ่านรายการ promo
   หรือรายการคอร์สที่ผูกกับ promo จากตารางโดยตรงได้
   ส่วน admin ที่ยังเปิดใช้งานบัญชีอยู่ต้องยังดูรายการ สร้าง แก้ไข เปิด/ปิด
   และลบ promo ได้ตามปกติ

หากตั้งค่า `SUPABASE_ACCESS_TOKEN` ไว้ในเครื่องแล้ว
สามารถใช้คำสั่งเดิมของโปรเจคแทนการเปิด SQL Editor ได้:

```powershell
node --env-file=.env.local scripts/apply-supabase-sql.mjs docs/sql/025_promo_code_security.sql
```

ห้ามนำข้อมูลลับหรือคีย์เข้า Git การตรวจ promo ใช้ session ของผู้ใช้ที่ล็อกอิน
จึงไม่ต้องใช้ service-role key ส่วนฟีเจอร์อื่นยังต้องใช้คีย์ตามข้อกำหนดเดิม

## ระบบทำงานอย่างไร

- `lookup_checkout_promo` ตรวจโค้ดที่ระบุสำหรับคอร์สหนึ่งคอร์ส
  และส่งกลับเฉพาะข้อมูลส่วนลดที่ใช้ได้กับราคาจากฐานข้อมูล
  โดยตรวจการล็อกอิน ช่วงเวลาที่ใช้โค้ดได้ คอร์สที่โค้ดครอบคลุม
  สถานะเปิดขายของคอร์ส และยอดซื้อขั้นต่ำ
- เก็บตัวนับไว้ในตารางส่วนตัวของฐานข้อมูล โดยแยกตาม `auth.uid()` หรือ ID ของบัญชี
  อนุญาต 10 ครั้งต่อช่วงเวลา 60 วินาที โดยเริ่มนับเวลาจากการลองครั้งแรก
  ตัวนับยังอยู่แม้รีสตาร์ตเว็บหรือรันเว็บหลาย instance
  และการเรียกฟังก์ชันฐานข้อมูลโดยตรงก็ใช้โควตาเดียวกัน
  เปลี่ยนโค้ด คอร์ส หรือ IP แล้วจะไม่ได้โควตาใหม่
  แต่ละบัญชีมีโควตาแยกกัน ข้อจำกัดนี้จึงเป็นการจำกัดต่อบัญชี
  ไม่ใช่การจำกัดต่อ IP หรือจำกัดจำนวน request รวมทั้งระบบ
- เมื่อตรวจโค้ดไม่ผ่าน ฟังก์ชันจะส่งผลลัพธ์กลับแทนการโยนข้อผิดพลาดของฐานข้อมูล
  เพื่อให้บันทึกจำนวนครั้งที่ลองผิดได้ ไม่ถูกย้อนคืนไปพร้อมข้อผิดพลาด
- การสร้าง/แก้ไข promo ของ admin ใช้ `save_admin_promo`
  โดยตรวจสิทธิ์ admin ซ้ำในฐานข้อมูล
  ข้อมูล promo และคอร์สที่ผูกไว้ทั้งหมดจะบันทึกสำเร็จหรือย้อนคืนพร้อมกัน
  หากส่งรายการคอร์สเป็นรายการว่าง หมายถึงตั้งใจให้ใช้ได้ทุกคอร์ส
  การแก้ไขจะคงสถานะเปิด/ปิดและช่วงเวลาที่ใช้โค้ดได้ตามค่าเดิม
- ฟังก์ชันฐานข้อมูลทั้งสองตัว หรือ RPC อนุญาตให้เรียกได้เฉพาะผู้ที่ล็อกอินแล้ว
  กำหนดตำแหน่งค้นหาออบเจ็กต์ในฐานข้อมูลไว้อย่างชัดเจน
  และไม่รับ ID ผู้ใช้หรือราคาที่ผู้เรียกกำหนดเอง
- การเปลี่ยนแปลงนี้ไม่ได้เพิ่มโควตาจำนวนครั้งที่ใช้สิทธิ์ส่วนลดสำเร็จ
  และไม่ได้เปลี่ยนสูตรคำนวณส่วนลดเดิม

## วิธีรันทดสอบ

```powershell
npm test -- promo admin-search-rate-limit
```

ไฟล์ `promo-security-db.test.js` ใช้ PGlite ซึ่งเป็น PostgreSQL ที่ทำงานในหน่วยความจำ
เพื่อรันไฟล์ SQL ที่เพิ่มขึ้นจริง และตรวจสิทธิ์เข้าถึงข้อมูล/RLS
การคงอยู่ของตัวนับ การหมดช่วงเวลาจำกัด สิทธิ์ผู้ใช้ และการย้อนคืน transaction

บัญชีและโครงสร้างฐานข้อมูลที่ใช้ทดสอบเป็นข้อมูลจำลองสำหรับการทดสอบ
ไม่ได้ใช้โครงสร้างฐานข้อมูล Supabase ที่เปิดใช้งานจริง
ส่วนการทดสอบ API ครอบคลุมการปลอมยอดซื้อ การเรียกโดยไม่ล็อกอิน
header ที่บอกเวลารอก่อนลองใหม่ การจำกัดโควตาในขั้นตอนจ่ายเงิน
และกรณีที่ยังไม่ได้รันไฟล์ SQL

การทดสอบเหล่านี้ไม่แก้ไขข้อมูลจริง และ PGlite เป็น dependency สำหรับการพัฒนาเท่านั้น
